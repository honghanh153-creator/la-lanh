# PR #342 reclassified S → L (fix-forward #353)

PR #342 (head `9d3f9e18`, merged into `collab/integration` as `1683ff5a`) declared **S**. It changes
the public v1 response of `POST /v1/daily-note/context` when the content gates reject every
candidate: before, `503 READING_UNAVAILABLE`; after, `422 READING_CONTENT_REJECTED`
(`apps/api/app/api/v1/routes/daily_notes.py:379`). A client that classifies or retries by status code
sees different behavior. Under `product-development-process.md` §0 an API/contract change is **L**.
Small diff size does not lower the level. This receipt records the L gates against what exists on
`origin/collab/integration`; it does not change code.

## Scope of `1683ff5a`

1. `apps/api/app/api/v1/routes/daily_notes.py`: `except ReadingContentRejected` placed before its base
   class `ReadingApplicationError`, returning `_reading_problem(422, "READING_CONTENT_REJECTED")`;
   the 422 response is documented as problem+json (`_REJECTED_RESPONSE`, `:45`). Other reading
   failures still return 503.
2. `packages/contracts/openapi/v1.json`, `packages/contracts/src/v1.ts`: regenerated; only the 422
   description text changes.
3. `apps/api/tests/daily/test_daily_api.py:134`: new regression test.

Not on `main` (`1683ff5a` is not an ancestor of `origin/main` at the time of writing).

## L gates

- **G1 Docs/contract.** OpenAPI JSON and the TS contract match runtime: the 422 description
  "Request input was rejected, or the reading content was rejected" is in `v1.json` and `v1.ts`
  (the PR reports `export_openapi --check`: current). The error code itself is not new; it comes
  from the insights routes (#209). **Gap:** no US/spec names `READING_CONTENT_REJECTED` for the
  Daily context route. US-03 §21 (`US-03-doc-note-hom-nay.md:476`) says a failed lens request keeps
  the sheet and old Note "để retry", which does not distinguish a content rejection (retry cannot
  help) from an outage. L requires the spec/US update; not done.
- **G2 UI/UX.** No UI change. **Gap:** the Home context sheet does not branch on the new code; a 422
  falls into the generic `onError` message (`apps/web/src/features/home/HomePage.tsx:188`), the same
  one shown for 503. No UX decision recorded for the content-rejected state on Daily.
- **G3 Copy.** No new user-facing copy. Any dedicated message for this state would be new copy and
  needs owner approval; not proposed here.
- **G4 BE/architecture.** Exception order is correct (subclass before base). Compatibility: the
  change is a breaking status change for this one failure path (503 → 422); it is recorded here and
  in the PR body. Only the web client calls the route (`apps/web/src/shared/api/client.ts:879`);
  `apps/mobile` has no direct caller. No architecture decision beyond reusing the insights pattern.
- **G5 FE.** `getContextualReading` uses the generated `ReadingProjection` type. The helper
  `isReadingContentRejected` (`client.ts:479`) exists but is used only by `InsightsPage.tsx:86`, not
  by the Daily context flow. The shared client has no automatic retry for this call, so the generic
  error path does not cause retry loops. **Gap:** no web test covers a 422 from the context route
  (`NoteDetailPage.test.tsx:95` mocks a 503 only).
- **G6 QC.** Covered: `test_context_projection_rejected_by_gates_is_a_content_error_not_a_503`
  (`test_daily_api.py:134`) forces `ReadingApplicationService.project` to raise
  `ReadingContentRejected` with a synthetic date-only profile and asserts status 422,
  `application/problem+json`, `Cache-Control: no-store, max-age=0`, code `READING_CONTENT_REJECTED`,
  and that the OpenAPI 422 response carries problem+json. The PR reports it red on old code
  (`assert 503 == 422`) and green after; `tests/readings/test_api.py:637` covers the same code on
  the insights side. **Not covered:** no test that other `ReadingApplicationError`s on this route
  still return 503; no manual QC script (required at L).
- **G7 Security.** Session and permission checks are unchanged and still run first (trusted
  Origin + CSRF at `daily_notes.py:355-356`). The 422 branch returns a fixed problem body, logs
  nothing itself, and the response is `no-store` (`_no_store`, `:351`). Short threat model: the new
  status lets a caller tell "content rejected" from "outage" for its own chart and lens only; it
  reveals no other user's data and no content. No new public endpoint, token, share link or
  dependency. No P0/P1 found.
- **G8 Privacy.** No personal-data field added, collected, stored, logged or sent to a third party;
  the data map (`docs/legal/store-privacy-data-map.md`) and store labels need no change. The test
  uses synthetic data only.
- **G9 Release.** Not released; integration branch only. Release to `main` needs an owner order.
- **G10 Cost/license.** No cost, licence or third party.
